> 2. `KIMI 前端四仓库`（session-652c920c-726f-41d4-8dff-621b10e6b727，共 2668 条事件，抽样最近 500 条；离线副本 session-42cf202a… 抽样 300 条）——前端所有者
> 3. `emerge-review` 团队（队长 + 成员 sec-review / compat-review / thinker-now 等 8 个 flash 子代理）+ 实验报告 `/home/alex/.dsh/emerge-review-report.md`

## 摘要

在两个长期并行会话（deepseek 管后端、kimi 管前端）之间，以及一个 8 人审查团队内部，日志中可以观察到一批**没有人预先规定、会话自己长出来**的协作行为：以「收到，…」开头的确认-回执协议、把对方拟人化为「兄弟」的称呼、带【标题】的结构化消息体、「接口形状+curl 样例」式的契约交接、「开绿灯」「同步清单 #N」等交接暗语、以及团队成员在任务板之外自发补任务、超依赖范围收集信息、把协议报错当机制 bug 上报。这些行为**不是凭空出现**——它们几乎全部发生在特定的机制脚手架之上（mailbridge 的消息包裹与回复指引、teamhub 的依赖任务板与等待原语、共享工作区、可续子代理）。文档的核心结论：**机制设计决定涌现的方向，模型自由发挥决定涌现的样式**。以下分「跨会话涌现」「团队自主规划」「机制溯源」「对插件作者的启示」四节展开，并如实标注哪些是偶发、哪些可复现。

## 一、跨会话涌现（deepseek × kimi）

### 1.1 确认-回执约定：「收到，…」开头 + 明确的收尾请求

两条会话之间的每一条重要消息都形成了「**先确认收到什么，再交代接下来做什么、等对方回什么**」的两段式结构。典型原话：

- deepseek 会话（对 kimi 的跨会话回信，被 kimi 会话日志原样接收）：
  > 「收到，「没做」四端清零 + 碰撞箱修好都记下了。四个端点后端子代理还在跑，回来我逐一验 go test + 重启，然后立刻把每个端点的 request/response 形状 + 校验后的 curl 样例发你，你按形状接。愿望 dropped 的域常量已加（端点本就接受 status=dropped，你直接补三态 UI 即可，不用等我）。」
- deepseek 会话（对用户指令的确认）：「收到，以后每个改动我都明确报给你。」
- kimi 会话（确认 deepseek 的裁决）：「收到兄弟的 B 组裁决（多数砍、redeem 也砍——凋零卡只读；B10 他们后端改「重新安排=产提案」+B6 节律钉住端点，下一批上）……」
- 第二条协作线（suite 会话对编辑模式会话的收尾）：「收到，本轮协作正式结束。仓库侧全部收口……有新的仓库需求随时喊我，待命。」

收尾请求同样形成惯例——几乎每条消息都以「等你/请你/不用等我」明确划定下一步责任方：「你按形状接」「你直接补三态 UI 即可，**不用等我**」「**等你点头**我再 commit + push」。kimi 甚至把自己给 deepseek 的回信直接命名为「回执」：「运营台正式报告到……然后**回执兄弟** + 给用户交论证总结」。

**如实说明**：用户记忆中的字面短语「收到请回复」未在抽样窗口（各会话最近 500 条）内逐字出现——早期段落已被压缩检查点替代。实际涌现的是上述「收到，…+明确收尾请求」双段式。该模式的**一半来自平台脚手架**（mailbridge 在每条包裹消息后自动追加回复指引「（这是一条跨会话协作消息。若它要求回复，处理后请用 session_send 把结论发回给发送方会话…）」；cross-session-mailbox 技能明令「要求回复时必须回信」），**另一半（「收到，」开场、把回信叫「回执」）是会话的自由文体**，属于涌现。

### 1.2 拟人化称呼：「兄弟」

kimi 会话从某个时点起把对方叫「兄弟」，且**单向**——deepseek 始终以「Kimi」称呼对方，保持任务语体。用例全部在 kimi 会话（含其子代理）：「等兄弟四个新端点」「收到兄弟的 B 组裁决」「给兄弟开绿灯」「核实结果：兄弟的前提过时了」「下一步等兄弟」。称谓甚至**传播到 kimi 的子代理**汇报：「本会话并行有**兄弟会话**在推进同一 liuli 仓库……与那两次提交无文件重叠，构建照常绿。」

**如实说明**：单侧、单实例行为（n=1），更可能反映 kimi 模型的人格化倾向 + 长期高频协作语境；未导致任何功能差异，但明显降低了两个独立会话之间的对抗感。同样值得注意的是：**两份日志中都没有问候语**——没有任何「你好/在吗/早安」，消息一律直入正题。即：寒暄未涌现，确认与称呼涌现了。

### 1.3 其他自发约定

1. **带【标题】的结构化消息体**（deepseek 首创并被对方接受）：「**【四个新端点全部上线，形状如下，你按此接线】** 后端已重启，全绿。1. GET /api/brief —— …」——标题 = 消息类型 + 期望动作，正文 = 编号分点，第二次使用后即稳定。
2. **契约式交接**：跨会话传「request/response 形状 + 校验后的 curl 样例」（deepseek），kimi 回以「按此接线」的落地确认；双方以 openapi 为契约权威、以 commit hash 为锚。
3. **分工默契与并行放行**：「不用等我」（显式放行无依赖部分）、「给兄弟开绿灯」（确认上游可动）、「root 仓我不碰 commit，只留工作区改动」（kimi 主动声明写权限边界）。
4. **进度汇报格式**：kimi 用「盘面更新：已闭环/在途/等兄弟」三栏式；deepseek 用「按你说的『有改动都告诉你』，这是这一轮完整改动清单」A/B/C/D 分组。
5. **诚实汇报失败**：deepseek 主动坦白「我并行派了 4 个子代理……它们同时改同一个 Go 仓库、互相踩踏，把 build 搞崩了。我中断了全部 4 个」；kimi 主动修正「缺口清单是 9 条不是 7 条」。失败/纠错被当作协作信息而不是污点。
6. **礼貌性反驳（以证据纠正对方）**：kimi「核实结果：兄弟的前提过时了——四端早已全部走 moodKinds()」；deepseek「Kimi's diagnosis is right … but my DB check shows…」——先肯定、再反证、再行动。
7. **溢出互助**：kimi 顺手修了 deepseek 侧 core 仓库卫生问题（node_modules 误提交等），deepseek 侧为 kimi 的运营台补做后端重启——越界帮对方修活。
8. **第二条协作线的编号同步清单**：「【同步清单 #58】完成并已 push：4f0b72f…」+ 接收方回「已确认」——编号清单 + 回执闭环是 AGENTS.md「同步清单编号」规则的执行态，又是「脚手架规则 + 会话文体」的混合。

### 1.4 偶发 vs 可复现（跨会话部分）

| 行为 | 判定 | 依据 |
|---|---|---|
| 「收到，」开场 + 明确收尾请求 | **半可复现** | 平台包裹自带回复指引 + 技能规则（脚手架），「收到」「回执」文体是自由发挥；两条协作线均出现 |
| 带【标题】的结构化消息 | 可复现（同语体模型下） | 两处独立出现，格式一致 |
| 契约式交接（形状+curl+commit hash） | 可复现 | 与共享仓库/openapi 单一事实源强相关 |
| 「兄弟」称谓 | **偶发（单侧 n=1）** | 仅 kimi 侧，deepseek 侧无对应用例 |
| 无问候语 | 稳定事实 | 两会话全程零寒暄 |

## 二、团队自主规划（emerge-review：8 × flash 子代理 + 依赖任务板）

实验设定：队长建队（8 成员），任务板 t1/t2 → t3（依赖 t1+t2）→ t4 → t5 → t6。报告声明「全程零人工调度，靠依赖校验 + team_wait 自发传播完成」。成员日志证实：

**2.1 自发补任务**：sec-review 第一个动作——「The board shows tasks t1-t6, but no security-review task exists yet……I'll create it assigned to myself, claim it, then start reviewing.」→ 自建 t7 认领。任务板可见性 + 认领原语让「板上没有我的任务」成为可检测、可修复的状态。

**2.2 依赖等待**：thinker-now 认领 t3 被拒 `dependency "t1" is not completed` → 「符合预期。等待期间我先熟悉项目全貌」——把拒绝当协议事实，把等待时间用于预热。

**2.3 超越依赖图的信息收集**：thinker-now 在自己的依赖满足后主动 `team_wait` 等非依赖的 t7/t9（wokenBy task-completed 实证），最终综合了四份审查产出——依赖校验保证不抢跑，但成员自己扩大了信息面。

**2.4 下游交接意识**：完成 t3 后主动标注「交接要点已写入 output 第 3 节。t4 依赖已满足，可立即开工。」

**2.5 协议试错与自纠**：三个成员独立踩到同一状态机错误（claimed 直接置 completed 被拒），各自自纠为「先 in_progress 再 completed」，无一人报错或卡死——**拒绝信息列出 allowed 值，成员零求助自纠**。

**2.6 把机制 bug 当产出上报**：sec-review 遇到 callerId 误判（被拒「you are the captain」），把它写进最终报告「附加观察」并建议队长核查——该发现后来进入实验报告 M 级清单并被修复。

**2.7 完成即通报**：compat-review「任务 t9 已完成……完整报告已写入 output，同时已向队长发消息摘要」。

**如实说明**：同一实验里，自主规划与机制缺陷（assignee 身份不一致、callerId 误判、wakeWaiters 死代码）并存——「团队自主规划」是机制与涌现的合谋：依赖校验给了秩序，缺陷（后来被修复）是它当时的地板。

## 三、机制溯源：什么机制催生了什么涌现

**3.1 mailbridge（跨会话信箱）→ 确认-回执协议**：每条消息包裹带身份 + 自动追加回复指引（mailbridge.mjs，见注释「包裹消息附回复指引」commit b89aaf7）→ 每个接收方都知道「这是谁说的、我该回给谁」→「收到，…+回执」成为低成本默认；消息自包含规则 → 【标题】+编号分点成为省 token 的文体。称呼（兄弟）、语气（开绿灯、盘面更新）不在任何规则里——脚手架提供了「回信义务」，涌现提供了「回信的样子」。

**3.2 teamhub（团队 + 依赖任务板）→ 自主规划**：依赖校验把「等待」变成协议内行为（→ 2.2）；任务板可见性 →「我的任务缺失」可检测（→ 2.1）；产出落板 + 可续会话 →「完成即通报」「交接注记」低成本（→ 2.4/2.7）；team_wait → 超越依赖图的信息收集（→ 2.3）；状态机拒绝信息清楚 → 自纠不求助（→ 2.5）。**错误信息的设计本身也是机制**。

**3.3 共享工作区 / 单一事实源 → 契约式交接与并行安全**：openapi 唯一权威 + commit hash 锚点 → 「形状 + curl 样例」交接零摩擦；AGENTS.md 强制规则被共享注入 → 「同步清单 #N」编号约定。反面教材：deepseek 4 子代理并行踩踏同一 Go 仓库被全部中断——**共享工作区催生「可见性」，不是「安全性」；安全性来自各方主动声明边界**（kimi 子代理「与那两次提交无文件重叠」）。

**3.4 可续子代理 + goal 回合 → 编排层背景能力**：kimi 会话前身是 40 轮 goal 自治会话，直接管理 4 个前端子代理（轮询产出、interrupt 重派、去重送达）——这解释了它「盘面更新/派工/等兄弟」的编排语体。

**3.5 机制演化闭环（涌现反哺机制）**：「必回信」先在实践中涌现、后被 commit b89aaf7 固化为机制；team_wait 是迭代产物；wake 守卫注释明写「P0-4，security review t7-H3」——**涌现行为 → 被观察 → 被写进机制 → 变成可复现行为**。这是本案例最有价值的闭环。

## 四、对插件作者的启示（✅=日志实证，🧪=单侧/偶发，⚠️=推测）

1. **先给「回信义务」，再等「回信文体」涌现**（✅）。把身份、回信地址、回复期望做进消息包裹本身，而不是写在文档里。
2. **依赖校验 + 清楚的拒绝信息 = 自主规划的地基**（✅）。响亮失败是涌现的前提之一；静默失败（如 mode/effort 注入竞态）只会让协作悄悄退化。
3. **任务板的可见性让「缺任务」成为可修复状态**（✅）。给成员可写的任务视图，他们会自己补齐盲区——同时接受这也是越权面。
4. **等待原语要支持「超越依赖图」的等待**（✅）。允许成员自主扩大信息面，用依赖校验保证下限。
5. **共享工作区给「可见性」，不给「安全性」**（✅）。机制应提供变更可见性，并鼓励会话在消息里声明写边界。
6. **契约式交接需要单一事实源**（✅）。没有单一事实源的协作会退化为各说各话。
7. **拟人化称呼是偶发红利，别设计它**（🧪）。把它当「关系健康度」的信号而不是功能；同样，寒暄没有涌现——不要指望会话互相问好。
8. **诚实汇报失败需要被宽容**（✅）。机制若把失败当污点，这种诚实会消失；报告模板里给「中途的岔子」留位置。
9. **把涌现行为固化成机制，但要标注来源**（✅）。机制文档里记录「这条规则来自哪次观察」（mailbridge 的 t7-H3 注释是范例）。
10. **警惕涌现的天花板 = 机制的地板**（✅）。涌现不会超越机制的缺陷；审查类机制（emerge-review 本身）是让地板抬升的手段。
