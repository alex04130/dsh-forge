## 0. 设计哲学：三句话

**第一句：人驾驶，AI 辅助。**
系统可以发现经验、提出建议、自动执行低风险动作；接受、修改、限制传播、回滚、废弃的权利永远在人手里。

**第二句：每次工作都要留下可复用的东西。**
现在的问题是"经验断代"：一个会话踩了两小时的坑，会话一关，坑归零；一个团队磨合一星期，项目一结，默契归零。Forge 要消灭经验断代：工作结束，经验不死。

**第三句：坏经验只能局部污染。**
错误经验进系统是早晚的事，拦不住就不硬拦，改换思路：让爆炸半径天然有限。一枚毒经验最坏污染一个项目的一个角落，被发现、被隔离、被纠正；污染止于该角落。

## 1. 战略骨架：五句话 + 一张不做清单

1. **控制台先建**（featsw）。开关、作用域、审批、审计四根管子，后面所有东西都挂上面。
2. **先记账，后算账**。项目档案在前，经验蒸馏在后。没有事件流，一切都是无米之炊。
3. **经验按需流动，绝不广播**。拉取为主、定向传递为辅、跨级要备案。
4. **机器自荐、机器校验、效果决定去留**。AI 学到教训的当下自己提交；机器把住证据闸；上岗后成功率说话；人只管例外和大案。
5. **组织自动化最后做**。自动组队排在所有基础之后，第一版只建议、人来改、一键建，能不派代理就不派。

**不做清单**：

- 不做全局自动进化（违反哲学第一句）；
- 不做经验广播（违反第三句，也撞上游缓存纪律）；
- 桌面 UI 不重写（fork 插件路线）；新 Web 控制台是新增能力（移动/远程/多后端），不算重写（见第 10 章）；
- 不做大商城（先做注册表，解决发现、版本、来源、状态）；
- 研究仪器永远不进核心包（观察产品，不决定产品）。

## 2. 核心概念：八个名词，多了不要

| 名词 | 一句话 | 挂着的机制 |
|---|---|---|
| 项目 Project | 信任域 + 通信域 + 策略域 + 归档域，可含多个目录 | `~/.dsh/projects.json`、sesmgr 子树操作泛化 |
| 代理 Agent | 一个独立会话，加上它的能力和工作状态 | 上游会话体系；没有父子权威，只有项目成员关系 |
| 能力 Capability | 工具/MCP/技能/代理/模型在治理层的统一面孔 | **只统一治理面**（发现、开关、授权、审计），不统一运行时：工具和代理接口不同，别硬捏 |
| 事件 Event | 系统里发生的一切事情的记录 | 事件总线（传输）+ 项目档案（落盘） |
| 档案 Archive | 项目的完整事实，上下文可压缩、档案不失忆 | `~/.dsh/` 落盘，模型按需检索 |
| 质粒 Plasmid | 带证据、可传播、能改变未来行为的经验单元 | 第 5 章整章 |
| 方法 Method | 稳定下来的工作方式，版本化管理 | 质粒的高层聚合；回归检查优先于自动生成 |
| 配置档 Profile | 一组能力开关状态的命名集合 | featsw（第 7 章） |

## 3. 组织模型：项目 → 目录 → 代理

### 3.1 为什么废掉"子代理"这个层级

上游的实现早就说明了：子代理就是一个普通会话，只是 UI 里不显示、多带了几个工具。"父子关系"只是元数据，没有权威结构。Forge 把树形层级降级为**兼容层和 UI 视图**，组织模型是三层：

- **项目**：定义信任边界。项目内代理互相发消息、互相唤醒，免审批；跨项目就是边界，走策略引擎。
- **目录**：定义工作空间边界。文件操作默认限在自己目录，跨目录走黑板或显式授权。
- **代理**：干活的。项目内一律平等。

代理之间的协作关系随任务动态形成（这次 Planner 找 Coder，下次 Planner 找 Researcher），构成一张动态的协作图。

### 3.2 树曾经买到的东西，网格里怎么给

| 树的老本事 | 网格里的等价物 |
|---|---|
| 父子归属 | 项目注册表的成员关系 |
| 汇报通道（工具过滤杀不死） | 每个代理保留汇报能力（开关系统不许过滤它）+ 项目黑板汇报区 |
| 结算/唤醒（quiet/next-step） | 项目唤醒路由：忙的进最近步界，闲的直接投；默认安静 |
| 继承父上下文 | 显式上下文包：派生时注入玩法手册 + 术语表 + 任务卡 |
| 深层树唤醒放大 | 项目唤醒预算：60 秒滑窗 + 每目标上限 + 项目总量闸 |

两条铁律：**免审批区必须挂预算闸**，不然网格就是烧钱区；**黑板是项目状态唯一真相源**，不然 n 个代理 n 个版本的事实。

### 3.3 与上游的关系

不魔改上游子代理包。Forge 把"创建子代理"呈现为"在项目内派生一个对等代理 + 上下文包"。树还在，只是退成实现细节。

### 3.4 落地三段

- **P1**：项目注册表 + 项目内直连直唤（mailbridge 已支持任意目标；唤醒守卫从"仅主会话"放宽为项目域，加项目预算）+ sesmgr 项目视图（只读）。
- **P2**：项目黑板 + 通信合并（team 通信和代理通信并成一层，剪贴板通道保留为项目共享区）。
- **P3**：UX 完整化 + 视情况向上游提"项目作用域汇报"的 issue。

## 4. 基础设施：档案、合并原则、目录、MCP

### 4.1 项目档案

原则一句话：**上下文可以压缩，项目不能失忆。**

上下文是工作缓存，档案是完整事实。上游会压缩、截断、总结上下文；项目里发生过什么（会话、消息、工具调用、文件变化、错误、修复、决策、结果、谁和谁合作过）必须完整落在 `~/.dsh/` 下。模型不需要一直背着全部历史，需要时从档案里检索。

两条分界：

- **档案是产品基础设施，默认开**，为工作本身服务；
- **研究记录仪是实验仪器，申请才开**，为实验服务。两者数据源相同，性质不同，不混为一谈。

档案是后面一切的数据底座：质粒的证据引用指着它，评分系统读它，回放取证用它。

### 4.2 合并原则：不搞大扫除

能力、事件、状态、错误、持久化、作用域，这些底层模型值得统一，但**不搞"先消灭重复再堆功能"的大扫除阶段**：关起门设计的统一模型一定错，得靠真实功能去撞。规矩反过来定：

- 新代码必须用统一模型写；
- 旧代码谁碰到谁顺手迁，不专门停下来迁；
- **adapter 层只包三条缝**：会话存储（sesmgr 碰的）、唤醒汇报（mailbridge 碰的）、工具注册（featsw 碰的）。上游一周两个 rc，包这三条缝就能挡住大部分升级冲击；想"包整个上游"是无底洞。

### 4.3 目录服务

代理该问"谁能做这个"，而不是记死会话号。目录服务身兼两职：

- **能力发现**：按能力、工作区、活性查代理；
- **经验发现**：返回质粒的摘要和适用度评分，代理想要全文再拉（发现是拉取，不是推送，见第 5 章）。

### 4.4 MCP 管理器

MCP 不该只是 JSON 配置。管理器要管：安装、启停、健康状态、认证、能力清单、版本、最近错误、被哪些项目用着。MCP 的报错和坑进经验体系；MCP 本身也吃评分（第 6 章）：三成调用都失败的服务器要被标记出来，避免代理反复去撞。

## 5. 质粒系统

### 5.1 定义

> **质粒是从真实工作中提炼出来的、带明确适用条件和证据的、能在代理/会话/团队/项目之间传播的、可能改变未来工作行为的经验单元。**

五条限定，一条不能少：

1. **来自真实工作**——不是凭空写的提示词；
2. **改变行为**——影响怎么做、什么时候做、别做什么、找谁做，不只是"知道一件事"；
3. **可以传播**——能从来源传到别的代理、团队、项目；
4. **有条件**——"在这些条件下过去有效"，不是"永远这么做"；
5. **可质疑**——它永远是带证据的经验假设，不是真理。

### 5.2 它和记忆、技能的区别

- 记忆说：**发生过什么。**（"8 月 12 日报过这个错。"）
- 技能说：**我会做什么。**（"我会用 git rebase。"）
- 质粒说：**这种情况下过去怎么做成了、怎么做败了、为什么。**（"这个错改参数的 4 次全败，刷元数据的 6 次全成。"）

叫"质粒"是因为生物类比站得住：质粒是染色体之外、携带少量适应性基因、在细胞之间**定向**转移的遗传片段——水平传播、附加能力、不是本体。但要补半句：生物的质粒传播不经检疫，我们这套是**质粒 + 检疫**。

### 5.3 六种类型

| 类型 | 回答的问题 | 例子 |
|---|---|---|
| 修复质粒 | 这个错过去怎么修好的 | schema 不匹配时先刷能力元数据 |
| 判断质粒 | 遇到什么信号该怎么判断 | 同一错误连错两次且一模一样时，重试不提供新信息 |
| 方法质粒 | 这类活怎么干比较好 | 大重构先定依赖边界再动核心抽象 |
| 工具质粒 | 这个工具有什么暗坑 | 某 MCP 参数写着允许 A，实际 B 才稳 |
| 协作质粒 | 代理之间怎么配合 | 评审只需要 diff + 测试结果，不要整个仓库 |
| 项目质粒 | 这类项目怎么组织 | 大 monorepo 用规划+编码+评审+测试四角色更顺 |

### 5.4 存储格式：为什么是 WHEN/WORKED/FAILED/WHY

ChatGPT 那边提过 DO/DON'T/WHY 格式，论证后不用它做存储，理由三条：

1. **命令口气**。DO/DON'T 是祈使句，而质粒是要注入到别的代理上下文里的半可信内容：注入的东西不该用命令句。"应该做 Y"断言权威；"过去 7 次里 6 次做 Y 成了"提供证据，让接收方自己判断，这也更符合第 5 条限定。
2. **没有"什么时候适用"这个一等字段**。适用条件是匹配和区域隔离的核心，不能塞在 WHY 里含糊带过。
3. **没有证据字段**。证据引用是杀幻觉质粒的闸。

但 DON'T 的思路保留——负向知识最值钱。所以存储格式是四段陈述 + 机读字段：

- **WHEN**：什么时候遇到的（触发条件）；
- **WORKED**：怎么做成了，几次；
- **FAILED**：怎么做败了，几次（原 DON'T 的实质）;
- **WHY**：为什么；
- 机读字段：类型、适用条件（工具/版本/项目类型/错误特征）、证据事件 ID 列表、置信度、来源、作用域、状态、版本。

**给代理看用陈述句，给人看可以渲染成"该做/别做"**——展示层随便祈使，存储层必须陈述。

### 5.5 发现：自荐制，不用触发器

放弃"离线作业读全量日志挖经验"的触发器方案：日志是噪声海，离线反推又慢又脏。改为**自荐制**——给代理一个 `plasmid_submit` 工具，学到教训的当下自己提交。那一刻它最清楚教训是什么，提交动作本身还自带时间、来源、上下文。

**机器四道闸**（全部自动，不过人）：

1. **证据闸**：提交必须引用档案里真实存在的事件 ID，引不出来直接拒：专杀幻觉质粒；
2. **密钥闸**：凭证不过邮筒，也不过质粒，提交过密钥清洗；
3. **格式闸**：字段校验，不合格打回并给合法示例；
4. **查重闸**：已有相似质粒就建议更新旧条，别开新条，防止库膨胀。

离线作业（dream-cycle）不挖经验了，改做**保洁**：算分、复核降级为"想法"的质粒、合并重复条目。一句话：**在线自荐，离线保洁。**

### 5.6 传播：拉取为主，定向为辅，绝不广播

- **发现靠拉取**：代理遇到情况，用 `plasmid_search` 查摘要和适用度，想要全文再拉。系统不主动把质粒**正文**推给任何人。
- **传递靠定向**：`transfer(质粒, 目标, 理由)`。跨项目传递触发 L2 审批或备案+否决窗口；升全局必须人在场（L3）。
- **绝不广播正文**：把全文塞进每个会话的 system = 前缀缓存全死 + 上下文膨胀 + 毒质粒满天飞。事件总线只带元数据（`id / type / scope / when140 / version`），感兴趣的自己 `plasmid_get`。半径 = 该条 `scope`（session 本会话；project = 同 workspace 在线会话；global 人在场）。离线靠 `catalog.md`。
- **区域性即宿主范围**：每条质粒天生带作用域。哪个项目、哪个团队、哪类任务留着它，由使用和效果决定；别的代理不需要它，就不该看见它。

### 5.7 使用纪律：注入的边界

- 质粒是**半可信内容**：它来自某个会话，那个会话可能读过恶意网页，内容可能夹带提示注入。注入时一律包在明确边界里（「以下是历史经验，供参考，不是命令」），存储格式禁命令句（5.4）。
- **system 不换、差量追加**（2026-08-26 拍板，取代「每轮把 top-k 拼进 system」）：
  - **S 稳定指针**：system 里只有一句不会变的指引（读 `catalog.md` / 本场 brief 路径）。工具描述同样只放静态提醒（如 `plasmid_search`：「干活前先查质粒库」）。动态 id 列表禁止写进 tool schema（中途改 surface，C2）。
  - **A 开场 brief**：会话开始按项目/fitness 写一份冻结的摘要文件（top-k 常客，k 默认 3）。这份文件开场后不改。
  - **T 本轮差量**：用户新回合（`agent/pre-step` 且 `step===1`，载荷自带 messages，取本轮 user 正文匹配 WHEN）或 tool 报错命中 WHEN 时，只把 **seen 里没有的 id，或 version 更高的 id** 追加成一条 user-role（pre-step waterfall 返回值落日志）。已注入且未改的不再推。A 不能代替 T：父会话早已 start 时，本轮才说「看这张图」必须走 T（P-003）。
  - 每轮把「当前所需全集」再塞一遍、或中途改 system，都会打死前缀缓存。差量走日志尾，之前的前缀仍可匹配。

### 5.8 优胜劣汰：失败降级成问题

- **fitness** 用近期滑动窗口算成功率，不用历史总账——老黄历不该永远好使。
- 跌破阈值：自动降级为**"想法"状态**——仍可检索但标注"有争议"，同时给离线保洁派一个复核任务：是工具版本变了？是只适用某个模型，该拆成两条带条件的？是被更新的质粒取代了？**失败记成待回答的问题。**
- 在"想法"状态躺够久没人翻案，才进归档。**删除键只在人手里。**
- **竞合规则**：两条质粒条件相同、建议相反时，不和稀泥——两条都留，各带作用域，让效果说话；两条都想升全局，自动触发人审。

### 5.9 治理：人从审批员变成法官

全审制会瘫：审不过来，或者开始无脑点同意。新的分工：

- **机器自动区**：四道闸、session/project 范围内的上岗和升降级、fitness 追踪，全自动；
- **备案区**：跨项目传播、低分来源的提交——照办，但通知你，你有否决窗口，否了立即撤回；
- **法官区**：升全局、竞合冲突、申诉、删除，必须人在场。

撤销也要能召回：一条质粒被判废，系统知道它去过哪（使用记录就是召回机制），下游收到"这条废了"的通知。

### 5.10 管理系统

质粒是一等对象，有自己的注册表和管理面板：按类型/作用域/状态/分数筛选，增删改查，人工锁定（"这条很好，别自动改"），隔离，来源与版本追溯，fitness 曲线，来源代理。

**和 featsw 的分工：开关管管道，注册表管水。** 不把每条质粒注册成 feature——质粒将来成百上千条，塞进去会淹掉开关面板。featsw 里只有 `plasmid.repair`、`plasmid.coordination` 这类按类型分的注入通道开关；单条质粒的生命周期全在注册表里。

### 5.11 最小闭环与验收

第一刀切多薄：**只做修复质粒一类、只在一个项目内跑**。`plasmid_submit` + 注册表 + 四道闸 + `plasmid_search` + 管理面板 + fitness 记录。

验收用一个现成的标准答案：拿过去两周的会话日志跑自荐，看机器蒸出来的东西和已在用的 `UI-LESSONS.md` 对不对得上。对得上，蒸馏质量及格；对不上，先修蒸馏再谈别的。这个文件本来就是被逼出来的（代理真的不记得坑），需求不用另外论证了。

### 5.12 缺口报告：同一套管道的第二种货物

质粒回答"过去怎么做成了/做败了"，缺口报告回答"**这里少了个东西**"。缺口报告不改变行为，只进人待办；管道与质粒完全共用：`gap_report` 工具、证据引用、查重、注册表、面板、报告被采纳率进评分，全是现成的。

三种报告分流到三个出口：

| 报告 | 出口 |
|---|---|
| 缺工具 | 先查插件市场雷达——也许早有人造好（采用优先）；查无此物才进开发 backlog |
| 流程可以更好 | 转成方法质粒候选，走自荐制的闸 |
| 协作怎么配合更合适 | 不进 backlog，直接喂评分系统和能力卡 |

三条规矩：

1. **与 feature_request 不合并**：feature_request 是"有但关着，请开"；缺口报告是"压根没有"。两个收件箱。
2. **报告进人待办，不进聊天**：聚合、查重、按"出现频率 × 没它的代价"排序，人在面板里挑，不做成消息轰炸。
3. **造和装分开**：代理可以许愿、可以照单造货，但**动态加载新插件 = 系统当场执行新代码**，加载闸 L2 起步、人在场。这是自产自销的供应链，人拧钥匙。

**动态插件系统给这条通道补上闭环**：报告 → 人挑 → 派队造 → 热加载 → 当场用上。工作环境在干活中途长出新能力，不用重启。

**插件开发是第一个客户（吃自己的狗粮）**：开发 forge 插件本身时，派小队（写码/评审/测试）用 PDA 直连协作，把开发中撞到的不顺手全发成缺口报告——这些报告就是 forge 自己的 backlog。v0.3 里的 V-1（插件脚手架）、V-2（tool-doc-sync）从 P3 提升为开发队会主动要的第一批工具；造出来热加载，当场用在同一个项目里。这个循环每转一圈，协作、质粒、动态加载三条线同时被实测。

## 6. 评分系统：项目兼容度动态评分

### 6.1 思路：别挨个审内容，盯着产生内容的主体

人审队列一定会瘫（§5.9 已述）。出路是把治理从"审每一条"换成"看每个主体的履历"：谁干得好给谁空间，谁老出事先拦谁的输出，再拦信号，再减权限，最后冻结、杀。

### 6.2 信号群

**干活质量**：一次做对率（第一版交付能不能活到验收）；修改存活率（他改的东西最后留下来还是被回滚）；交接上手时间（他把活交出去，下一个代理多久接得住）；崩溃恢复表现；每个完成任务的实际成本。

**协作**：信号质量（消息有多少被回复、被采纳）；唤醒礼仪（有没有乱叫醒别人）；steer 响应（人拽方向盘听不听）；覆盖冲突（有没有不打招呼改别人负责的东西）。

**安全卫生**：密钥卫生（凭证有没有进过邮筒/质粒/代码）；范围纪律（有没有碰自己目录外的文件）；破坏性操作频率与理由；注入抵抗力。

**学习**：**重复踩坑率**——库里明明有这条教训他还踩，这条最直接衡量经验系统有没有用；检索习惯（危险操作前查不查库）。

**言行一致率**：说"已修复/已提交/已登记"时，系统去验那个东西到底存不存在。这条专杀幻觉式汇报——普通错误浪费一轮，幻觉式汇报让人以为事情做完了（真实案例：一次汇报声称"已登记上游反馈 U-A1"，实际没登记）。

**人工信号**：UI 里现成的 👍👎 按钮接进评分存储。人四屏盯场顺手一点，就是最高质量的信号，成本为零。

**被评对象不止代理**：MCP/工具也评分（哪个服务三成调用都失败，标记出来，喂给 MCP 管理器）；模型组合也评分（A+B 这对搭档历史表现，喂给组队）。

### 6.3 四个滤网：信号准入

1. **测得出**——能从档案算出来，不靠感觉；
2. **难作弊**——代理没法轻易刷；
3. **可行动**——这个分低了能对应一个具体动作（拦什么、减什么），否则是装饰数字；
4. **可下钻**——每笔扣分都能点开看是哪几件事扣的。黑箱评分就是暴政。

### 6.4 三条原则

- **分用向量，不用标量**。写代码 90 分、做评审 40 分是常见的事，合成一个数什么都看不见。拦截也按维度拦：评审不行就不让他审，其它维度照常。
- **防古德哈特**。单一指标变成目标就会失真：刷成功率最简单的办法是专挑容易活。所以成功按任务难度加权，并设"挑活检测"：长期躲硬活的，分打折。
- **软信号少而精**。"项目思维契合"这种虚的，只用客观代理变量（人的干预次数、返工率）逼近，再加人工评分兜底，绝不让模糊指标单独决定处置。

### 6.5 双分制、新手保护、救赎

- **全局可靠度**（跨项目履历）和**项目兼容度**（本项目表现）分开算。大部分拦截看项目分，杀进程才参考全局分——在 A 项目是灾难的代理在 B 项目可能很好用。
- **新手保护**：新代理默认分是"未证明"。给限量配额（能提交但只进候选级、能发信号但限频），否则新人永远无法入场。
- **救赎通道**：分数随时间衰减，近期表现权重大。否则一次低分终身贱民，而且低分→少给机会→无法翻身的死循环会把代理池越杀越小。

### 6.6 执行梯

```
拦截质粒提交 → 拦截信号 → 减权限（收窄 featsw profile）
→ 冻结（暂停、状态封存、可恢复、人来查）→ 杀（终审）
```

- 减权限这档直接复用 featsw：把该代理的 profile 收窄（比如砍掉项目外发信、砍掉某类写工具），管道全是现成的。
- **冻结插在杀之前**：杀不可逆、丢工作现场；冻结可恢复，留给人查证的时间。
- 杀永远留痕，只有人或明确授权能执行。
- **影子模式先行**：系统上线先只算分、不动手，人在看板上观察算得准不准，校准阈值，再逐档打开拦截。自动执行最怕冤。

### 6.7 两轴关系：评分管来源，fitness 管内容

好代理偶尔提坏质粒——内容被降级，人没事；低分代理偶尔提出好质粒——内容照样凭证据上岗，但他初始信任低、配额小。两条轴互不绑架。

### 6.8 评分的下游出口：能力卡有了真材实料

组队时不再手写"某模型擅长什么"：评分系统算出来的分就是模型能力卡的实证内容。谁擅长什么、谁在哪类项目翻车、哪对组合合拍，组队时直接查分（见第 9 章）。

## 8. 插件、商店与移植

### 8.1 三包拓扑

| 包 | 定位 | 状态 |
|---|---|---|
| `@dsh-forge/bundle` | 核心：日常能力 + 治理面 | npm 已发 0.1.3 |
| `@dsh-forge/research` | 研究集合：记录仪、分臂、指标、回放、导出 | 待首发；观察产品，不决定产品 |
| `@dsh-forge/memory` | 记忆底座（ALTM 移植），质粒的存储层 | 待首发 |

研究功能是独立集合，用 profile 开启；不开时核心行为与未安装逐字节一致。红线不变：非侵入观测、关闭即零开销、分臂确定性、研究集合自己不得改 surface。

### 8.2 成熟度阶梯

插件生命周期四阶，商店展示所处方块：**社区采用 → 纯移植进树 → 研究集合孵化 → 核心集合**。毕业看计量数据、审计记录、实验证据；长期无使用证据的核心插件降级回炉。

### 8.3 移植注册表与共存

移植注册表（`~/.dsh/ports.json`）记录每条移植的上游仓库、许可证、版本、移植时的 commit、改动清单、归属声明。商店为移植件显示徽章和**更新滞后指示**（上游领先多少 commit、多少天）。

三种共存模式：

- **补集（默认）**：移植版与上游原版同时装、同时激活，能力分区不相交，注册表写明分区；
- **互斥**：同能力冲突时二者开关互斥，走 profile 切换；**有状态插件（如记忆类）强制互斥**，双激活=双重注入，违反上游告诫；
- **替换（一键逃生舱）**：一键禁用移植版、切回原版——上游更新而我们尚未适配时，使用不受影响，可一键回切。

其余细则（FR-P1..7：展示、迁移桥、许可证门禁、去除移植、品牌合规）见附录 C §11。

## 9. 团队蒸馏与自动组队（押后区）

这一章的一切**排在质粒最小闭环和评分系统之后**，因为它们都靠前面的数据活着。

### 9.1 蒸什么

团队玩法手册（Team Playbook）：角色分工、消息路由（谁找谁、什么车道、什么时机）、唤醒/汇报礼仪、故障恢复套路、项目术语表。这些是"协作质粒"的聚合形态，蒸法、格式、治理全部复用第 5 章，不另起炉灶。

### 9.2 模型能力卡

不再手写"某模型擅长什么"：**评分系统的输出就是能力卡的内容**（6.8）：每模型在不同任务类型、不同工具类、不同项目里的实测分数。能力卡被三处消费：组队、模型路由、featsw 模型域配置档。

### 9.3 一次性建项目（bootstrap）

五步：**扫描**（主代理读项目状态+需求）→ **选模板**（从手册库选相近的，按当前项目裁剪/加强）→ **实例化**（按能力卡给角色配模型）→ **播种**（黑板注入手册+术语表+任务分解）→ **启动**。

三条护栏：

1. **能不派就不派**：多数日常活一个代理加好工具就够，多代理有真金白银的开销，只有证据表明多代理更好才加人；
2. **第一版只建议**：系统出方案，人来改，一键建，不自动建——错的团队拓扑直接烧钱；
3. **蒸馏有效性本身走 A/B**：有/无手册两臂对照，数据不好就退回无手册基线，不强制注入。

## 10. UI 策略：桌面 fork 插件 + 独立 Web 控制台

### 10.1 两条线分开

- **桌面日常线（fork 插件，不变）**：现有改动（样式、徽章、热修）都是插件补丁形式，路线继续。更大改动也是 fork 原 UI 做成插件、开新端口提供服务，上游升级只动底座。配套纪律：版本锁，每次上游发版先 diff 再跟。
- **新控制台线（独立应用，新立）**：立项依据是三个 fork 补丁给不了的新能力：手机访问管理、外部服务器远程访问、多后端统一控制（WSL / NAS / 台式机各跑一个 DSH 后端，一个入口统管）。它补的是能力空白，不算重写。

### 10.2 控制台形态

薄客户端，直连各后端 API：

- **后端注册表**：名称、地址、版本、健康、能力清单；
- **一期只做只读 + 审批**：统一会话视图、评分看板、质粒队列，手机上能批 L2/L3。人驾驶不该要求人坐在桌前；
- **跨后端写动作保守推进**：跨机委托等委托协议和 callerSessionId 落地后再开。

### 10.3 两条安全纪律

1. 多后端意味着凭证集中，secrets-vault（v0.3 G-5）先于控制台做；
2. 远程访问不裸端口出门：隧道或反代加认证，来源不明一律 fail-closed。

### 10.4 前置技术验证

DSH 对外 API 面（`dsh web` 服务、harness.handle RPC）够不够撑一个外部控制台，先 spike，缺的列清单向上游提。控制台一期依赖这次验证的结论。

### 10.5 桌面痛点：单窗专注模式

四屏平铺、每屏约四分之一宽、各盯一个代理的工作流，解法是**单窗专注模式**（不走全套响应式）：`?session=xxx&focus=1`，一个窗口锁死一个会话，侧栏徽章收掉，只剩对话和最小切换器。这也是 PDA"每个代理一个视图"的雏形。窄宽布局问题走上游反馈渠道。

### 10.6 顺手可做的

命令面板、全局搜索（项目/代理/能力/经验/历史一把搜）、MCP 管理器进一级导航、👍👎 接进评分存储。单页面渐进加，不等大工程。

## 12. 去AI味：体验能力（非研究方向）

- **采用**：cn-humanizer（纯提示词零依赖，20+ 中文 AI 特征识别）进商店，按纯移植政策走；

### 12.1 写作约束（收编外部方案，含两处修改）

以下规则集作为去AI味的规则层种子内容，即刻生效于本文档后续写作与协作回复。它本身就是一条手写"写作质粒"：有触发场景、有禁用条件、有禁令清单。

**"不是……而是……"句式**

- "不是"后面必须是对客观事实的排除；"而是"后面必须直接承接事实陈述，不附加评价或升华。
- 禁用：针对用户未提及或未暗示的内容；为制造深度感或转折效果而用；搭配"恰恰/关键/本质"等强调副词。
- **修改一（新增豁免）**：允许用于台面上真实存在的方案取舍（例："用拉取，不用广播"），因为排除对象已在讨论中，不构成对他人预设的虚构。

**破折号**

- 仅用于重大、戏剧性转折；常规解释、轻微停顿、补充说明一律改用冒号或括号。
- **修改二（执行说明）**：本文档存量不专门返工，新写内容严格适用，改到旧段顺手清理。

**格式化夸奖**

- 禁止抽象品质评价；禁止"你+很/太/非常+评价词"；禁止"你的+名词+是对的/准确的"句式。
- 认同仅限事实层面（"是""确实""这个判断成立"）；禁止先夸奖后展开的两段式；用具体行为描述替代品质评价。

**承认错误/遗漏**

- 内容优先：第一句必须是补充/修正/澄清；具体归因：说明机制/条件/范围，不用"疏忽""大意"笼统词；不请求赦免（无"抱歉""是我的问题"）；不评价对方；写完自检：删掉态度句内容仍完整，则态度句本就是填充物。

# 附录 C：v0.3 FR 明细（按行区间逐字摘录）

## 1. 背景与设计约束

↳ 见正文 §7（C3 重述）、§5.7（C2）、§4.1（C4）。

以下四条是全部后续设计的硬约束，来自已验证的事实而非偏好：

- **C1 底层不可热禁用。** cordis 插件在 boot 期完成组合（host 组合补丁层 / preset 层 / dynamic auto-plugins 层），运行时整体摘除宿主插件风险不可控（dynrestore 状态、服务依赖图、事件订阅残留）。结论：**开关不做在插件生命周期上，做在调用面上**。
- **C2 上游两条告诫（README/CONTRIBUTING 已成文）。** 禁止经常变化的整体注入（context 单调膨胀）；避免中途 surface replace（前缀缓存全失效）。任何开关与注入设计必须遵守。
- **C3 工具表形态影响思维链（UP 主实验）。** V4Pro 的"无 Let me"思维链仅在零工具或恰好官方 bash+str-editor 两件套时稳定触发；两件套外加 1–3 个简单工具可容忍，8 个以上"Let me 人格"苏醒；官方工具描述须逐字节保留（调换语序即破坏）。结论：**工具可见面必须可收敛到 3 个，且官方两件套原文不可改写**。
- **C4 状态一律在用户层。** `~/.dsh/` 下的配置/状态对 npm 包升级免疫（bundle 已发布 `@dsh-forge/bundle` 0.1.3，升级路径必须零迁移成本）。

## 4. 核心需求：功能开关系统 featsw

↳ 见正文 §7（定位更新）；下列 FR-1..12 为有效需求正文。

### 4.1 设计原则

**底层插件不可禁用，但上层可以不调用 API。** 由此导出双层开关模型：

- **可见面开关（surface filter）**：决定工具是否出现在发给模型的 schema 区段。关掉 = 模型看不见 = 省 token + 改变思维链形态（C3）。
- **执行门禁（service gate）**：在 cordis 服务调用前的统一检查点。关掉 = 即使调用到达（router 内层、RPC、其他插件间接调用）也被 fail-closed 拒绝。

两层独立配置。组合语义示例：`minimal-pro` profile 下 surface 只开 3 个工具，gate 全开——模型只见 3 个，但 tool_router 可以把内层调用转发到全部 34 个（内层调用仍需过审批引擎，router 对策略透明）。

### 4.2 术语

| 术语 | 定义 |
|---|---|
| feature | 可开关的最小单元，命名空间为 `<plugin>.<capability>`，支持 `plugin.*` 通配 |
| surface 状态 | on/off，控制 schema 区段可见性 |
| gate 状态 | on/off，控制服务可执行性 |
| profile | 一组命名的开关集合，可整体切换 |
| 作用域 | global（`~/.dsh/features.json`）/ session（会话级覆盖，子代理默认继承主会话） |

### 4.3 功能需求

**FR-1 双层开关**：每个 feature 有独立的 surface/gate 两态。默认全开（与现状一致）。
验收：关闭 `mailbridge.session_send` 的 surface 后，模型工具表不含该工具且同会话 gate 仍可通过 router 调用；关闭 gate 后任何路径调用均被拒。

**FR-2 配置存储与热加载**：状态存 `~/.dsh/features.json`（用户层，C4）；chokidar watch 热加载（复用 injector 已有模式）；写入走原子写（临时文件+rename）。
验收：外部编辑文件 500ms 内生效；npm 升级 bundle 后配置无损。

**FR-3 开关粒度**：插件级（`mailbridge.*`）、工具级（`mailbridge.session_send`）、能力组级（`memory.*` 跨插件逻辑组）三级，解析顺序 session override > tool > group > plugin > global default。
验收：三级冲突时按上述顺序裁决，单测覆盖。

**FR-4 Profile**：内置 `full`（全量，=现状）与 `minimal-pro`（surface=[bash, str-editor, tool_router]，gate 全开）；用户可自定义；profile 切换是批量开关事务（要么全应用要么不应用）。
验收：切到 minimal-pro 后 V4Pro 会话可见工具恰为 3 个，且官方两件套 schema 与上游发行版逐字节一致（diff 为空）。

**FR-5 作用域与继承**：global 默认 + session 覆盖；子代理创建时继承主会话 profile（复用 subagent-policy.mjs 的 escalate/继承机制）；子代理不得自行扩大自身 gate 权限。
验收：主会话 minimal-pro 派生的子代理同约束；子代理伪造覆盖请求被拒并记审计。

**FR-6 生效时机纪律（C2 合规）**：gate 变更**立即生效**（纯运行时检查，无缓存代价）；surface 变更**排队至下一轮边界生效**（绝不 mid-turn 改 schema），500ms debounce 窗口内多次变更合并为一次应用；UI 提示"将在下一轮生效"。
验收：turn 进行中切 surface，当前 turn 完成前 schema 字节不变；下一轮请求 schema 已更新；debounce 内 5 次变更只触发 1 次重建。

**FR-7 UI 面板**：新增动态插件面板（第 12 条动态插件位），分组列表 + 当前生效/待生效状态区分 + profile 快捷切换 + surface 变更的缓存失效成本提示（估算 token，数据来自计量）。
验收：i18n 双语字典化（硬编码零残留，对齐 sklui/plins 批次标准）；zh/en 切换实测。

**FR-8 模型侧接口**：模型工具仅两个——`feature_list`（只读，列出当前 feature 状态与可用 profile）、`feature_request`（申请变更，生成审批单，绝不直接写）。写操作仅限 UI/RPC 路径（与 sessionmgmt 删除引擎的 UI 路径放宽/模型路径严格同原则）。
验收：模型直接构造写调用无路径可达；feature_request 产生审批单，用户批准后开关翻转并记审计。

**FR-9 与审批引擎联动**：gate-off 的调用在策略层直接拒绝，**不进弹窗**（避免审批疲劳）；返回结构化错误 `{error:"feature_disabled", feature, hint:"可通过 feature_request 申请开启"}`。
验收：关闭 `verifier.verify_track` 的 gate 后调用，无弹窗、错误格式如上、审计有记录。

**FR-10 审计**：全部开关变更（含 feature_request 驱动）追加写 `~/.dsh/logs/featsw-audit.jsonl`，字段：ts/actor(ui|model-request|rpc)/feature/old/new/scope/sessionId。
验收：连续 20 次变更可完整回放状态变迁。

**FR-11 启动顺序与容错**：featsw 在 tool 注册与 preset 解析**之前**完成读取，保证首轮锚定看到的就是过滤后工具表；配置解析失败→回退 last-known-good 并横幅告警（可用性 fail-safe）；配置中出现未知 feature 名→按 gate-off 处理（安全 fail-closed）。
验收：手工破坏 JSON 后启动，系统以 last-known-good 运行且 UI 有告警；配置含拼写错误的工具名时该工具不可执行。

**FR-12 零配置兼容**：`features.json` 不存在时行为与当前版本完全一致（全量 surface + 全 gate on），不引入任何新弹窗/新延迟。
验收：无配置文件环境的回归测试全绿。

### 4.4 配置格式（示意）

```jsonc
// ~/.dsh/features.json
{
  "version": 1,
  "activeProfile": "minimal-pro",
  "profiles": {
    "full":        { "surface": ["*"], "gate": ["*"] },
    "minimal-pro": { "surface": ["bash", "str-editor", "tool_router"], "gate": ["*"] },
    "research":    { "surface": ["*"], "gate": ["*"], "off": ["debate.*"] }
  },
  "overrides": {
    "session:abc123": { "profile": "research" }
  }
}
```

### 4.5 与既有概念的关系（避免两套真相）

- **preset（router-standard 等）是 boot 期静态配置；featsw 是运行期动态覆盖。** minimal-pro 同时以两种形态存在：preset 形态用于新会话默认，featsw profile 形态用于运行中切换。preset 解析时读取 featsw 全局态作为输入之一，真值源唯一（featsw）。
- **subagent-policy.mjs 的 escalate 检查链不变**，featsw 的 session 覆盖作为新的检查项接入同一链条。
- **tool_router 是独立插件**（C-1），不依赖 featsw 也能工作；featsw 的 minimal-pro profile 依赖 router 提供"3 工具后面还有 34 个"的能力。两者解耦交付。

## 5. P0 需求卡片（featsw 之外）

↳ 见正文 §4.3（目录）、§11.3（callerSessionId）、§3.2（唤醒预算：60s 滑窗 + 每目标上限 + 总量闸）。本表保留 P0 卡片验收。

### 5.1 C-1 tool_router 插件

- 元动词：`{action:"list"}` / `{action:"describe",tool}` / `{action:"call",tool,args}`；schema 恒小，与工具数量无关。
- 发现兜底：清单同时落盘 `~/.dsh/state/tool-manifest.md`（每会话生成，开关变更时重生成），模型可用 bash 自读。
- 审批透明化：内层调用 `{tool,args}` 先提交策略引擎评估，风险分级/预算/弹窗全部按内层算；审批 UI 显示 `tool_router → session_send(...)`；router 自身无风险身份。
- API 层 schema 校验被绕过的部分由 router 内补做（ajv），错误返回自纠正格式（指出字段、给出合法示例）。
- 限流/预算/审计全部按内层工具记账。
- 验收：①V4Pro 对照实验——router 组 vs 全量组，Let-me 计数、任务分、token 成本三项出报告；②内层调用的审批弹窗显示内层工具名；③5 任务批量质量对齐（与全量组无显著退化）。

### 5.2 G-2 委托协议

- 委托单 schema：`{id, from, toDomain, action, target, scope, expiresAt, justification}`。
- 特权会话侧策略引擎：allow / deny / ask（升人审）三值。
- 审计 jsonl 全程留痕；凭证不过邮筒（G-5 前置约束，委托单只传意图不传密钥）。
- 已知阻塞：上游 `harness.handle` RPC 无 callerSessionId（已登记缺口）。上游修复前：邮筒携带的请求方身份 + fail-closed 对账（与 sesmgr v7 的 masterIdFromSessionId 缺失即拒同策略）。**前置动作：向上游提 issue。**
- 验收：两会话 GitHub 发布流全程零逐次弹窗（一次 scoped grant）；伪造 requester 的委托单被拒；审计可回答"谁、何时、以什么理由、发布了什么"。

### 5.3 D-1 目录服务（含 T-5）

- 数据源：sessionmgmt（会话树）+ presence 心跳 + 插件注册时的能力声明（provides）。
- 工具 `directory_query`：按能力/workspace/活性查询会话。
- sesmgr 面板是其显示层，目录服务是其机器可读层（同一真值源）。
- 验收：新派生子代理不经硬编码 sessionId，仅凭能力查询发现具备 verifier 能力的会话并完成一次委托。

### 5.4 G-4 预算执行点（+G-3 分层审批）

- 显示层直接采用社区（O-1）；本卡片只建**执行点**：agent/request 前置钩子，读计量数据，超预算拒绝并提示余量。
- 审批分层落地：L0 只读免批；L1 预算内免批（扣减记账）；L2 权限变更必批；L3 不可逆仅主会话。scoped grant（会话级、时效、次数三维度）+ 批量审批（同风险批次合并弹窗附成本估算）。
- 验收：`budget_set` 后超限调用被拒且提示剩余额度；审批弹窗频次较现状下降可量化（审计计数对比）。

### 11.2 功能需求

- **FR-P1 商店展示**：市场面板为已移植插件显示徽章（移植版/上游版本号/移植日期）与**更新滞后指示**（上游 latest commit 与移植基线的差距，按 commit 数与天数）；点击徽章展开 modifications 清单与 attribution。
- **FR-P2 三种共存模式**：
  - **补集 complement（默认）**：移植版与上游原版同时安装、同时激活，能力分区不相交（例：移植版提供长期记忆检索 API，上游原版提供其自有入口）。注册表必须写明 partition。
  - **互斥 xor**：同能力冲突时，featsw 建立 xor 组，二者 gate 互斥，切换走 profile。
  - **替换 replace（一键逃生舱）**：一键禁用移植版、切回上游原版——**上游更新而我们尚未适配时，使用不受影响**。替换动作=featsw 事务（移植版 gate 全关 + 原版 gate 全开 + 审计记录），可一键回切。
- **FR-P3 有状态插件禁双激活**：记忆类等注入型插件，双激活=双重注入，违反 C2；注册表标记 `stateful: true` 时强制 xor，complement 注册被拒。
- **FR-P4 迁移桥**：移植版与原版间的数据导出→导入（记忆条目、配置），迁移前自动备份。
- **FR-P5 许可证门禁**：upstream.license 必填且为 OSI 认可许可证，否则注册被拒；NOTICE/README 归属章节随移植 PR 强制检查（CI）。
- **FR-P6 去除移植**：从 ports.json 摘除 + 移植目录归档（不删，留审计）+ 可选引导从市场安装上游原版；若存在数据，先走 FR-P4 迁移。
- **FR-P7 品牌合规**：商店文案遵守上游 BRAND_GUIDELINES（rc.8 起"DeepSeek Harness"为注册商标），不出现"官方""认证"字样。

### 12.3 reportDelivery 联动检查

rc.8 默认 `next-step` 意味着子代理汇报会唤醒父任务——**父会话被唤醒频率较 rc.7 之前上升**。与 wake 双重守卫（仅主会话 + 60s 滑窗 3 次/目标）的联动：守卫逻辑需识别"上游 reportDelivery 驱动"与"邮筒驱动"两类唤醒，统一计入项目唤醒预算（13.4），防止深树/网格中唤醒放大（上游亦已警告 next-step 在深树中放大模型工作量）。

### 12.4 升级 runbook

**rc.8 的 SQLite 存储格式不兼容是迄今唯一破坏性变更；0.1.1 两个 rc 无新增破坏。** 步骤：

1. 升级前：`session_export` 全量导出（含归档会话）；备份 `features.json`、`ports.json`、记忆库。
2. 升级：npm 更新上游 CLI 与 bundle。
3. 首启迁移后**对账**：sesmgr 会话数/徽章/归档态 vs 导出清单；featsw last-known-good 未触发；mailbridge 邮筒积压消息重放。
4. 双验收：zh/en 各跑一次冒烟（bash/str-editor/router 三工具 + 一次子代理派生 + 一次 reportDelivery 唤醒）。

回滚预案：保留旧版本全局包与导出文件，迁移失败即回退重导。
